# TeXFlux DSL v1 言語仕様

## 1. ステータスと設計目標

本書は、TeXFlux v1 の利用者向け言語仕様書である。言語の規範的な定義（Normative Specification）は
`texflux_tex_first_dsl_v1_spec.md` に記載されており、実装、README、各種サンプル、テスト、
そして本書の記述もすべてその定義に準拠しなければならない。

TeXFlux は、「TeX-first」を掲げるインデントベースのプリプロセッサである。TeX 本文そのものを
解析・エスケープ・正規化することはせず、主に文書構造に関する以下の要素のみを簡潔に記述できるようにする。

- TeX 環境（environment）の `\begin{...}` / `\end{...}`
- 構造化コマンド（command）の必須引数（required argument）
- リテラルな TeX の中括弧グループ（`{ ... }`）
- `itemize` 環境などの定型的なリスト構造
- 値の入れ子関係を表現する合成（composition）

v1 の中心的な設計モデルは、「**suite（インデントブロック）が値を生成し、container / command / special がその値を消費する**」というものである。suite の形式は以下の3種類のみである。

~~~text
suffix なし  = 右辺（RHS）ですでに完結している単一の値
:           = suite 全体を1つの複数行ブロック値とするブロック（block）
::          = '-' ごとに1つのブロック値を生成するシーケンス（sequence）
~~~

## 2. プレフィックス（Prefix）

行頭やセグメント先頭に付くプレフィックス（接頭辞）の意味は字句的に決定され、TeX パッケージやテンプレート、コマンド登録情報（レジストリ）、あるいは既知のコマンド引数の数などには一切依存しない。

~~~text
\   TeX コマンド（command）
@   構造コンテナ（structural container）
!   TeXFlux の特殊変換（special transformation）
~~~

`@` は名前付き TeX 環境（`\begin{...}`〜`\end{...}`）専用ではない。v1 で利用可能な `@` コンテナは以下の通りである。

~~~text
@name             名前付き TeX 環境コンテナ（named TeX environment container）
@{}               無名のリテラル中括弧コンテナ（anonymous literal TeX brace container）
@{RAW_TEX}        先頭に生の TeX コードを含むリテラル中括弧コンテナ
@                 無名の透過コンテナ（anonymous transparent container）
@:                透過コンテナのブロックスイート
@::               透過コンテナのシーケンススイート
~~~

通常の TeX コマンド行は、そのまま生の TeX（raw TeX）として扱われる。ただし、トップレベルに構造化 suffix（末尾の `:` または `::`）またはスタック区切り文字（`>>`）を含むコマンド行は、構造化構文の候補として解釈される。
未知の名前を持つ環境（unknown named environment）であっても構文としてそのまま受け付けられ、LaTeX 側での解決に委ねられる。一方、未知の special（unknown special）はエラーとなる。

## 3. 物理行とインデント

入力テキストの改行コード（CRLF / CR）はすべて LF に正規化される。タブ文字（tab）は raw mode 領域の内側を除いて使用できない。出力末尾には必ず改行が1つ付加される。

構造を表すインデントは、半角スペース4個（ASCII space 4文字）単位である。suite の直下の子要素（direct child）は、その階層の基準インデント位置（suite base）に配置しなければならない。生の TeX コード（raw TeX）行における余分なインデントはそのまま保持されるが、不適切な追加インデント位置に構造化構文の候補が置かれている場合は構文エラーとなる。空行（blank line）の扱いは suite のモードによって異なる。

構造化構文と認識される位置で、文字どおりの `@` / `!` から始まる生の行を出力したい場合は、`@@` / `!!` と記述してエスケープできる。先頭の1文字だけを取り除き、残りは生の TeX 行として扱う。ブロック内では構造化構文の追加インデント検査より前に処理され、基準位置より余分な字下げを保持する。シーケンスの `-` の直後の payload にも使える（`- !!bar` → `!bar`）。raw mode 領域の外ではタブ禁止の規則は変わらない。

~~~text
@@literal-at
!!literal-bang
~~~

展開後:
~~~tex
@literal-at
!literal-bang
~~~

`!!` 単独は `!`、`!!!foo` は `!!foo`、`!!重要` は `!重要` を出力する。エスケープした行では、不均衡な `{` や末尾の `:`、`>>` もそのまま残る。

長い生の TeX 領域には、行頭 escape ではなく `!BEGIN_RAW_MODE` / `!END_RAW_MODE` を使う。
マーカーは前後の半角スペースを除いてマーカー文字列だけからなる行でなければならず、BEGIN はそのブロックの基準位置に置く。
BEGIN の次の物理行から、同じインデントの END の直前までが raw mode 領域になる。

~~~text
@lstlisting:
    !BEGIN_RAW_MODE
    def f(x):
    [TAB]return !x
    @foo{bar
    !!baz
    !END_RAW_MODE
~~~

領域内の行はヘッダー、`:`、`>>`、`@@` / `!!`、空行の巻き戻しを一切解釈せず、先頭の半角スペースを基準位置の分だけ（最大でその数まで）取り除いてそのまま出力する。領域内ではタブも許可され、`!text{...}` も補間されない。BEGIN / END 行は出力されない。インデントの異なる `!END_RAW_MODE` と領域内の `!BEGIN_RAW_MODE` は本文として出力されるため、リテラル END は別のインデントに置く。`-` の payload や `>>` のセグメントにはできない。

raw mode はブロックを書ける場所（トップレベル、`:` の本文、シーケンス entry の継続ブロック、マクロテンプレート）で使える。ただし `.tfxm` のトップレベルは従来どおり純粋性検査の対象であり、空行・コメント以外の生の本文を置けない。

## 4. ヘッダースキャナ（Header scanner）

ヘッダースキャナは、グループ内部を TeX コードとして解釈・展開することはない。必須グループ、オプション引数グループ、Beamer のオーバーレイ指定グループについて、括弧の対応（バランス）を保ちながら機械的に走査する。

~~~text
{...}   必須グループ（required group）
[...]   オプション引数グループ（optional group）
<...>   オーバーレイグループ（overlay group）
~~~

`!` セグメント、かつ `!` セグメントのみが、これらすべてのグループの後にさらに1つだけグループを持つことができる。末尾の `(...)` 束縛リスト（binding list）であり、これは `!import` が読む（14章）。`(` はそれ以外のどこでもグループを開かない。したがってコマンドヘッダー、環境名、生の TeX は、`(` を通常の文字として読む。

各グループ内部に含まれるコロン（`:`）、パイプ（`|`）、二重山括弧（`>>`）は、常に解釈されない不透明な生テキスト（opaque raw text）として扱われる。トップレベル行の末尾にあるコロンと、前後を空白で区切られた `>>` だけが構造化トークン（structural token）として認識される。行末以外にコロンを含む通常のコマンド行は、そのまま生の TeX として扱われる。なお、ヘッダー末尾に置く TeX 形式のコメント（`% ...`）は v1 ではサポートされない。

なお、グループ外の行末にある `>>` は次の物理行への継続を表す（10.3 節）。この場合、`>>` の後の空白を改行が代わりに担う。

suite を開始する suffix（接尾辞）としては、以下の形式のみを受け付ける。2つのコロンは空白を挟まずに続ける。

~~~text
:
::
~~~

単独のコロン `:` は**ブロックモード（block mode）**、空白を挟まない二重コロン `::` は**シーケンスモード（sequence mode）**を表す。suite suffix の後ろに他のトークンを置くとパースエラーとなる。パイプ `|` は suite の構文ではなく、生の TeX 行に含まれる場合はそのまま保持される。

既存の通常の TeX の書き方で、コマンド名の直後に括弧が密着した `\foo(x):` は、この移行によって再分類せず、生の TeX のまま扱う。ここでの `(...)` は束縛リストではない。この互換例外は `::` には適用されず、`\foo(x)::` は構文エラーになる。
通常のコマンドでは、単独のコロンの後ろに空白以外の文字が続く場合は suffix ではないため、`\texttt{std}:vector` は生の TeX のまま扱う。ただし `|` と `>>` は例外で、旧来のパイプ suite や壊れたスタックヘッダーを静かに raw TeX へ戻さず、エラーにする。`::` を認識した後ろにトークンが続く `\texttt{std}::vector` もエラーになる。

`@` から始まるコンテナの字句分類は、以下の優先順位で行われる。

~~~text
@{...}  リテラル中括弧コンテナ（literal brace container）
@       透過コンテナ（transparent container）
@name   名前付き環境コンテナ（named environment container）
~~~

`@{...}` のグループはヘッダーに含まれる生の TeX であり、「名前が空の環境」として扱ってはならない。対応する括弧で囲まれた中身について、TeXFlux が内容をパースしたり妥当性を検証したりすることはない。

スタック（`>>`）を構成する各セグメントには、必ず完全なプレフィックス（`\`、`@`、`!`）を明示しなければならない。プレフィックスを省略する記法は存在しない。

~~~text
@{} >> @center >> @{\small}
~~~

以下の例はプレフィックスが不足しているため無効（invalid）である。

~~~text
@{} >> center >> {\small}
~~~

## 5. シーケンススイート（Sequence suite）

末尾が二重コロン（`::`）の行に続く suite は、`-` で明示された値エントリー（value entry）の並び（シーケンス）を表す。構造化コマンドのシーケンススイートには、少なくとも1つのエントリーが必要である。各 `-` が1つのブロック値の開始を示し、同じインデント階層にある次の `-` の直前までがその値に含まれる。したがって値の境界は `-` のみによって決定される。生成される中括弧がその値に密着するか独立行になるかは、値が1行に収まるかどうかで決まる（15章を参照）。

~~~text
\foo::
    - A
      continuation of A
    - B
~~~

展開後:
~~~tex
\foo{
A
continuation of A
}{B}
~~~

エントリー間に挟まれた空行（blank line）は単なる区切りとして無視される。

~~~text
\foo::
    - A

    - B
~~~

上記の例は「A」と「B」という2つのブロック値を表しており、間に第3の空の値が生成されるわけではない。この空行は値の一部にはならない。

~~~text
\foo::
    - short arg
      continuation
    - another arg
~~~

`-` と同じ物理行に書かれたペイロード（文字列）は、そのブロック値の先頭行となる。後続の行がそのエントリーよりも深くインデントされていれば、同じ階層の次の `-` が現れるまで、同一ブロック値の継続行（continuation）として TeXFlux の通常のブロックパーサーにより処理される。`-` の行自体にペイロードが書かれていなくても、後続の深くインデントされた行群がブロック値となる。

~~~text
\foo::
    - short arg
      very long
      multiline
      argument
    - another arg
~~~

展開後:
~~~tex
\foo{
short arg
very long
multiline
argument
}{another arg}
~~~

なお、「`- |`」というブロックマーカーは存在しない。「`|`」は単なるペイロードの文字として扱われるため、複数行の値を記述する場合でも記号は `-` のみ（bare の `-`）を使用する。

シーケンスエントリーのブロック内には、生の TeX 行だけでなく、プレフィックスを伴う構造化式（structural expression）を配置することもできる。

~~~text
\foo::
    - @center:
        BODY
    - @{\small}:
        SMALL BODY
    - @center >> \includegraphics{fig.pdf}
~~~

シーケンスエントリー内の構造化式によって生成された値は、1つのまとまった値として親のコマンドやコンテナに渡される。

## 6. ブロックスイート（Block suite）

`:` は、それに続く suite 全体をちょうど1つのブロック値（exactly one block value）として扱う。

~~~text
\foo:
    A
    B
    @center:
        C
~~~

展開後:
~~~tex
\foo{
A
B
\begin{center}
C
\end{center}
}
~~~

ブロック内部に含まれる生の行、ネストしたコンテナ、special、スタック構文などは通常どおり解析される。また、ブロック内部の空行は保持される。

~~~text
\foo:
    A

    B
~~~

展開後:
~~~tex
\foo{
A

B
}
~~~

`:` に続く suite は空であってもよい。例えば、空の透過値（transparent value）は以下のように記述できる。

~~~text
@:
~~~

空のブロックは出力を生成しない。

## 7. コマンド（Command）

構造化コマンド（structured command）とは、トップレベル行の末尾にコロンを伴うか、またはスタックセグメント（`>>`）として記述される `\` プレフィックス付きのコマンドである。ヘッダー部分にインラインで記述されたコンパクトグループ（`{...}` や `[...]` など）は、suite から渡される値よりも先に出力される。

シーケンスモードでは、受け取ったすべての値を順に必須引数（`{...}`）として消費・出力する。

~~~text
\foo{COMPACT}::
    - A
    - B
~~~

展開後:
~~~tex
\foo{COMPACT}{A}{B}
~~~

ブロックモードでは、ブロック全体を1つの複数行必須引数（long required argument）として展開する。

~~~text
\foo:
    A
    B
~~~

展開後:
~~~tex
\foo{
A
B
}
~~~

シーケンス内の構造化された値は、1つの必須引数グループ（`{...}`）の中に内包される。そのため、リテラル中括弧コンテナ（`@{}`）の中括弧が引数自体の外側の中括弧に吸収されて消えることはない。

~~~text
\foo::
    - @{}:
        A
        B
~~~

展開後:
~~~tex
\foo{
{
A
B
}
}
~~~

suite やスタック構文（`>>`）を伴わない通常のコマンド行は、そのまま生の TeX（raw TeX）として出力される。

~~~text
\foo{A}{B}
~~~

構造化されたシーケンスエントリーの内部や、スタックの終端（terminal）に置かれたコマンドは、すでに完結した正準な値（canonical value）として扱われる。

## 8. 名前付き環境（Named environment）

名前付き環境（named environment）は、LaTeX の `\begin{...}` と `\end{...}` のペアを生成する。未知の環境名やアスタリスク付きの環境名（例: `@tabular*`）であっても、構文として正しければそのまま受け付けられる。

ブロックモード（`:`）では、ブロック値全体が環境の本文（body）となり、ヘッダーに記述されたインライングループは `\begin{...}` 側の引数となる。

~~~text
@frame{Title}:
    Hello
    @center:
        World
~~~

展開後:
~~~tex
\begin{frame}{Title}
Hello
\begin{center}
World
\end{center}
\end{frame}
~~~

シーケンスモード（`::`）では、**最後の値が環境の本文（body）**となり、**最後以外の値はすべて環境の必須引数（required block arguments）**となる。この割り当ては、レジストリやテンプレートの知識を必要とせず、構文規則のみに基づいて決定される。

~~~text
@myenv::
    - ARG1
    - ARG2
    - @:
        BODY1
        BODY2
~~~

展開後:
~~~tex
\begin{myenv}{ARG1}{ARG2}
BODY1
BODY2
\end{myenv}
~~~

シーケンスの最後のブロック値に含まれる正準ノード群が、そのまま環境の本文となる。

エントリー（値）が1つも存在しないシーケンス環境はバリデーションエラーとなる。空の本文が必要な場合は、末尾に空ブロック（`@:`）を明示的に記述する。

~~~text
@myenv::
    - ARG1
    - ARG2
    - @:
~~~

旧記法から移行するときは、旧シーケンスの `\foo:` を `\foo::` に変更する必要がある。`-` エントリーを持つ旧記法をそのまま残すと、現在の構文では有効なブロック suite として解釈され、複数の引数ではなく1つの複数行引数になるため、静かに出力が変わる。旧ブロックの `:|` / `: |` はエラーになるので `:` に変更する。

箇条書きも、専用の構文ではなく通常の環境として記述する。`\item` は生の TeX であり、オーバーレイ指定（`<...>`）もラベル（`[...]`）も TeX のまま書ける。入れ子は `@itemize` を入れ子にする。

~~~text
@itemize:
    \item<1-> 最初の項目
    \item<2->[※] 特記事項
    @itemize:
        \item サブ項目
~~~

展開後:
~~~tex
\begin{itemize}
\item<1-> 最初の項目
\item<2->[※] 特記事項
\begin{itemize}
\item サブ項目
\end{itemize}
\end{itemize}
~~~

環境の本文は通常のブロックスイートなので、その中の各行にも2章から7章までの規則が
そのまま適用される。`\item` 行も例外ではない。したがって、リストの項目本文に
書ける文字列は、文書のどこに書く生の TeX 行とも同じ制約を受ける。

| 書きたい行 | 起きること | 書き方 |
| --- | --- | --- |
| `\item まとめ:` | パースエラー（行末のコロンは予約されている） | `\item まとめ:{}` |
| `\TextCA{注意}::`（項目の継続行） | パースエラー（シーケンススイートには `-` エントリーが必要） | `\TextCA{注意}:{}` |
| `@foo{A}` | パースエラー（環境ヘッダーとして読まれる） | `@@foo{A}` |
| `!foo` | ディレクティブエラー（special として読まれる） | `!!foo` |
| `\item >> \foo` | **エラーにならず**スタック合成として読まれ、`\item{` / `\foo` / `}` の3行になる | `\item` と `>>` の間に本文を置く |
| `@@foo{A}` / `!!foo{A}` | **エラーにならず** `@foo{A}` / `!foo{A}` になる（`@@` / `!!` が行頭のエスケープとして解釈される） | `@@@foo{A}` / `!!!foo{A}` |

下2行だけはエラーにならずに出力が変わる。移行時にはこちらのほうが危険である。

末尾に空グループ `{}` を足す方法は、TeX の出力を変えない（空グループは
`\spacefactor` に触れないため、コロンが設定する文末スペースも保たれる）。
本文を次の行へ送ってもよい（`\item` だけの行は完結したコマンド行として
生の TeX になる）。

ブロックスイートは空行を文書の内容として保持する。項目の間に空行を置くと、
生成される TeX にもその空行が残る。

行頭が `!` の生の TeX 行は `!!` で書ける。`@verbatim` や `@lstlisting` の本文も
通常のブロックスイートなので、`!important` は `!!important`、`!! # ...` は
`!!! # ...` と書く。余分な字下げも保持される（3章）。

## 9. 無名コンテナ（Anonymous containers）

### 9.1 透過コンテナ（Transparent container）

`@:` は外側のラッパー（`\begin` や中括弧など）を一切出力せず、ブロック値に含まれるノードをそのまま出力する。

~~~text
@:
    A
    B
~~~

展開後:
~~~tex
A
B
~~~

`@::` のシーケンス形式は、複数の値を1つの透過的な合成値（transparent composite）にまとめる。空のシーケンスも許容されており、その場合は何も出力されない。なお、リテラル中括弧コンテナ（`@{}::`）で空シーケンスを指定した場合は、空の TeX 中括弧グループ（`{}`）が出力される。複数行の空の値を明示したい場合は、`@:` または `@{}:` を使用する。

~~~text
@::
    - A
    - B
~~~

これをコマンドの引数の中で使用すると、「A」と「B」がまとまって1つのブロック値としてコマンドに渡される。

### 9.2 リテラル中括弧コンテナ（Literal brace container）

`@{RAW_TEX}:` は、常に実際の TeX 中括弧グループ（`{ ... }`）を出力する。波括弧内の `RAW_TEX` は、先頭の生の TeX コード（leading raw TeX）としてグループ内の先頭に配置される。

~~~text
@{\small\color{red}}:
    BODY
~~~

展開後:
~~~tex
{
\small\color{red}
BODY
}
~~~

このリテラルグループの中括弧は、コマンドの引数内、環境の本文内、あるいはスタックの途中など、どのような文脈であっても削除されたり外側の中括弧に吸収されたりすることはない。

## 10. スタック合成（Stack composition）

二重山括弧 `>>` は、純粋な構造的合成（pure structural composition）を表す。スキャナがセグメントの並びを保持し、正規化処理（normalization）によって右から左へと入れ子の値ツリー（nested value tree）に変換される。そのため、最終的なレンダラーは `>>` の存在を意識しない。

### 10.1 閉じたスタック（Closed stack）

suffix を持たないスタックにおいて、最右端のセグメントがすでに完結した値（closed value）であれば、そのスタックは有効である。

~~~text
@center >> \includegraphics{fig.pdf}
~~~

展開後:
~~~tex
\begin{center}
\includegraphics{fig.pdf}
\end{center}
~~~

多段の合成も同様に記述できる。

~~~text
@frame{Title} >> @center >> @{\small} >> \input{fig.tex}
~~~

最右端が `@name`、`@`、`@{...}` などのように値を受け取る余地を残したオープンなコンテナ（open container）であるにもかかわらず、その値（payload）が与えられていないスタックは無効（invalid）である。

~~~text
@foo >> @center
~~~

### 10.2 開いたスタック（Open stack）

suite を後続させる場合、suffix（`:` または `::`）は最右端のセグメントに付与する。

~~~text
@frame{Title} >> @center >> @{\small}:
    BODY
~~~

この場合、最右端のリテラルグループ（`@{\small}`）が後続のブロック値（`BODY`）を受け取り、それによって完成した値が手前の `@center`、さらに `@frame{Title}` へと順に渡される。

末尾が二重コロン（`::`）の場合も同様に、最右端のセグメントにシーケンス値群が渡される。

~~~text
\outer >> \inner::
    - A
    - B
~~~

まず `\inner` が「A」と「B」を引数として消費してコマンドの値を完成させ、その完成した値が `\outer` の1つのブロック引数値となる。

スタックセグメントに固有の複雑な終端規則はない。suffix を持たないスタックの最右端だけが完結した値（closed value）である必要がある、というシンプルなルールである。

### 10.3 行末の `>>` による継続

構造化ヘッダーのグループ外にある `>>` の直後で改行できる。

~~~text
@hoge >>
@fuga >>
@fuge:
    foobarhoge
~~~

これは、同じ本文を持つ `@hoge >> @fuga >> @fuge:` と同じ結果になる。先頭行を `@hoge >> @fuga >>` として、残りだけを次の行に置いてもよい。

末尾が完結した値なら、suffix は不要である。

~~~text
@hoge >>
@fuga >> \foobar
~~~

継続先は直後の物理行とし、最初のヘッダー行と同じインデントに揃え、完全なプレフィックス（`\`、`@`、`!`）から始める。空行やコメントを挟むこと、継続先の欠落、インデントの変更はパースエラーになる。`>>` の前には空白が必要で、行末の `>>` の後には空白を置いてもよい。

suite を付ける場合、suffix は最後のヘッダー行の最右端セグメントに置き、本文は通常どおりヘッダーの基準から4スペース深くする。シーケンスの `- @hoge >>` から継続する場合、継続行は `-` の位置に揃え、マーカーを繰り返さない。その suite はマーカーより4スペース深い位置から始まる。複数の物理行にまたがるシーケンス値には、既存の複数行用の引数中括弧配置が適用される。

生の TeX と `@@` / `!!` でエスケープした行では、行末の `>>` は継続を意味しない。グループ内部を改行で分割することもできない。セグメント・グループ・suffix の位置情報は元の物理行を指し、構文 AST では従来と同じ1つの `Stack` になる。

## 11. 特殊構文（Specials）

Special は `!` で始まる。未知の special は `DirectiveError` になる。ハンドラは TeX 文字列を直接返すのではなく、正準 AST ノード（canonical AST node）のタプルを返す。

組み込みとして残っているのは、モジュール構文の `!import` と `!macroimport` のちょうど2つだけである（14節）。どちらもハンドラではなくコンパイルセッションが解決する。組み込み名なので `!defmacro` で再定義することはできない。

### 11.1 標準フロー制御

フロー制御は言語の組み込みではない。`!before` / `!after` / `!around` / `!off` / `!drop` は、コンパイラに同梱された1つのマクロモジュール（14.10節）で定義された**ただのソースマクロ**である。すべての `.tfx` と `.tfxm` が、import を書かずにこの5つを使える。

この5つの名前は予約されている。`.tfx` でも `.tfxm` でも、同じ名前を `!defmacro` で定義するとバリデーションエラーになる。shadowing（上書き）はしない。

`!before` / `!after` / `!around` は、ペイロードの前後に値を1つずつ置く。

~~~text
!before{\smallskip} >> \foo
!after{\smallskip} >> \foo
!around{\vspace{-1em}}{\vspace{2em}}:
    contents
~~~

`!around{A}{B}` は `!before{A} >> !after{B} >>` の合成と同じ結果になるが、「前後で1組」という操作は1つの概念なので独立した名前を残している。

`!off` は最初の値を捨ててペイロードだけを残す。合成の途中から1セグメントを外す書き方である。

~~~text
\fuga >> !off{\foo{a}{b}} >> \hoge
~~~

これは `\fuga >> \hoge` と同じ結果になる。`!drop` はペイロードだけを受け取り、何も出力しない。

~~~text
!drop >> \hoge >> \fuga
~~~

この5つには12節のマクロの規則がそのまま適用され、固有の規則は1つもない。`':'` の suite で渡すペイロードと `>>` の残りとして渡すペイロードは同じ1つの値であり（12.2節）、`'::'` のシーケンススイートも他の呼び出しと同じく `-` 1件につき1値になる。値の個数が合わなければ通常の arity 診断が出る。provenance も通常のマクロと同じで、各値は著者が書いたグループや suite のスパンを保つ。

`!drop` にも専用のプリミティブは要らない。テンプレートが空なので、束縛した値はテンプレートのどの位置にも現れず、展開後には何も残らない。フェーズの挙動もこれで決まる。捨てられたペイロードは正規化も content import の解決もされないので、`!drop:` の中に `!import` を書いてもそのファイルは開かれず、未知の special や値として消費できない形も報告されない。

ただし捨てられるペイロードもマクロの値なので、**捨てられる前に展開はされる**。したがって展開段階のエラー——引数の数が合わないマクロ呼び出し、トップレベル以外の `!defmacro`、テンプレート外の `!param` / `!each`、再帰、補間のエラー——は報告される。これは捨てられた `!when` / `!unless` の payload（13.5節）より**弱い**。あちらは展開そのものを行わない。コンパイルが通らなくなった箇所を黙らせたいときは `!when` / `!unless` を使う。`!drop` は「展開は通るが今は要らない」内容を捨てるためのものである。

### 11.2 削除された `!vpad`

かつての `!vpad` は削除され、別名としても残っていない。余白は著者が選んだ生の TeX であり、それを置く位置だけを汎用のコンビネータが決める。

~~~text
!before{\vspace{-1em}}:
    contents
!around{\vspace{-1em}}{\vspace{2em}}:
    contents
~~~

こうすることで、言語側に `\vspace` を知っているハンドラは1つも残らず、特定の構文の引数だけに補間を許す許可リストも不要になる。

## 12. ソースマクロ（Source macro）

ソースマクロは、単なる文字列置換マクロではなく、**値・コンテナ・スタック合成（`>>`）の上に構築された構造的な AST マクロ（structural AST macro）**である。テンプレートは構文 AST として保存され、マクロ呼び出し側で渡された値をパラメータにバインドしてクローン（複製）される。ソーステキストの単純な置換や、レンダリング後の TeX の再パースは一切行われない。テキストフィールドへの文字列展開は `!text` に限って行われ、挿入された文字列は再走査も再パースもされない（12.7節）。

### 12.1 !defmacro

~~~text
!defmacro{name}{param}{...rest}:
    TEMPLATE
~~~

マクロの定義には `:` ブロックスイートのみを受け付ける。`::` のシーケンス形式はバリデーションエラーとなる。最初の必須グループがマクロ名であり、後から `!name` として呼び出せるよう special 名の文法規則に従う必要がある。2つ目以降の必須グループがパラメータ名となる。マクロ定義自体は TeX コードを出力しない。定義行の前後に置かれた空行は、通常の文書コンテンツとして保持される。

マクロの定義は**トップレベルのみ**で許可される。他のマクロテンプレートの内部を含め、トップレベル以外の場所に置かれた `!defmacro` はバリデーションエラーとなり、動的な定義は行えない。すべての定義をあらかじめ収集した上でマクロ呼び出しを展開するため、定義より前の位置でマクロを呼び出す前方参照（forward reference）が可能である。

~~~text
!foo >> \TextCA{A}

!defmacro{foo}{body}:
    @{\small} >> !param{body}
~~~

パラメータ名には `[A-Za-z_][A-Za-z0-9_-]*` の文字パターンが使用できる。パラメータ名の重複、予約名（`defmacro`、`param`、`text`、`each`、`flag`、`when`、`unless`、`BEGIN_RAW_MODE`、`END_RAW_MODE`）の使用、組み込みの special と同名の使用、標準フロー制御（11.1節）と同名の使用、およびマクロ自体の多重定義は、いずれも定義位置（definition site）を指し示すバリデーションエラーとなる。

### 12.2 値のバインド（Value binding）

マクロ呼び出しには、既存の値構文がそのまま適用される。マクロ専用の特別な呼び出し構文は存在しない。値のバインドは左から順に行われ、ヘッダーに記述されたインラインの必須グループが先、suite が生成する値が後になる。

~~~text
!foo{A}{B}          インライン値 2個
!foo:             ブロック値 1個
!foo::             '-' ごとにブロック値 1個（シーケンス）
!foo >> VALUE       閉じたスタックのペイロードを1個の値として
~~~

したがって、例えば `!foo{A} >> \bar{B}` という記述は `[A, \bar{B}]` という2つの値をバインドする。オプション引数グループ（`[...]`）やオーバーレイグループ（`<...>`）は値ではないため、マクロ呼び出しに付与することはできない（エラーとなる）。

通常のパラメータは**ちょうど1つの値（exactly one value）**を受け取る。末尾に `{...rest}` のように記述した可変長パラメータ（rest parameter）は、残りのすべての値をシーケンスとして受け取り、0個の値であっても許容される。rest parameter は省略可能かつ一意であり、必ずパラメータリストの最後に置かなければならない。引数の個数（arity）が一致しない場合は、マクロ名、期待される引数形式、実際の引数の数、および呼び出し位置のスパンを含むマクロエラーとなる。

### 12.3 !param

`!param{name}` は、テンプレート内でバインドされた値の AST をその位置に挿入する。必須グループをちょうど1個だけ取り、suite は取らない。テンプレート外での使用、未バインドのパラメータ名の指定、および rest parameter の指定は、すべてマクロエラーとなる。rest parameter は単一の値ではなくシーケンスであるため、後述の `!each` を通じてのみアクセスできる。

`!param` は AST を挿入するため、不透明な TeX グループの内部には展開できない。テキスト中の `!param{...}` はエラーになる。グループ内へ文字列を差し込むには `!text` を使う（12.7節）。AST を渡す場合は、以下のような構造化された形式を使用する。

~~~text
@infobox::
    - !param{title}
    - !param{body}
~~~

### 12.4 !each

~~~text
!each{rest-param}{item}:
    TEMPLATE
~~~

`!each` は、rest parameter に格納された一連の値を出現順（source order）に走査し、各要素を一時変数 `item` にバインドしながらテンプレートを展開して、その結果を外側のブロックへ順に連結する。シーケンスが空の場合は何も生成されない。`:` suite を伴う必要があり、マクロテンプレート内でのみ有効である。第1グループには必ず rest parameter を指定しなければならない。すでにバインドされているパラメータ名を覆い隠す（シャドウイングする）変数名を指定した場合はマクロエラーとなる。なお、`!each` はネストして使用できる。

`!each` は、スタックの末尾 suffix が `:` である場合に限り、スタックの最右端セグメントとして配置できる。これは、最右端セグメントがその suffix を受け取るため、自身で `:` を持っているのと等価になるからである。

~~~text
@{\bfseries} >> !each{items}{item}:
    \item
    !param{item}
~~~

スタックの最右端以外の位置に置いた場合は、suite が合成（synthetic）扱いとなってしまうためバリデーションエラーとなる。また、`!defmacro` をスタックセグメントに含めることはできない（合成すると左側のセグメントの下にネストされ、マクロ定義がトップレベル文ではなくなってしまうため）。

### 12.5 展開（Expansion）

マクロ呼び出しは、常に**1つの値**（展開されたテンプレートブロック）として扱われる。したがって、`>>` の合成チェーンの途中にマクロ呼び出しを配置することも可能である。

~~~text
@center >> !smallred >> \TextCA{Important}
~~~

マクロテンプレート内から別のマクロを呼び出すことも可能である。ただしマクロの再帰呼び出し（recursion）は禁止されており、直接的・間接的な循環参照はすべて明示的に検出され、循環経路を含むマクロエラーとなる。

~~~text
recursive macro expansion detected: foo -> bar -> foo
~~~

マクロの展開は、`>>` の脱糖（desugaring）が行われた後、値の消費（value consumption）が行われる前に実行される AST-to-AST パスである。マクロ固有の構文が正規化処理やレンダラーに漏れ出ることはない。なお、スプライス構文（`!splice`）は v1 には含まれない。

### 12.6 ソースマッピング（Source mapping）

`!param` から出力されたコードは、マクロ呼び出し側（call site）で渡された元の値の位置情報（source span）を保持する。一方、テンプレート自体に由来する構造・枠組み（scaffolding）の位置情報は、定義位置ではなく**マクロ呼び出し位置（macro call site）**へとリターゲットされる。これにより、逆方向検索（SyncTeX inverse search）を行った際、ユーザーが書いた本文をクリックした場合はその本文の記述位置へ、マクロが生成した枠組みをクリックした場合はマクロ呼び出し行へと正確に戻ることができる。

### 12.7 文字列 interpolation（`!text`）

`!text{name}` は、テンプレート内のテキストフィールドに、バインドされた値の文字列を
差し込む。名前はパラメータ名と同じ `[A-Za-z_][A-Za-z0-9_-]*` で、`text` は
マクロ名として予約される。`!param` は AST の挿入、`!text` は文字列の挿入を行う。

~~~text
!defmacro{figure}{name}{width}{caption}:
    \includegraphics[width=!text{width}]{fig/!text{name}.pdf}
    @center:
        @minipage{!text{width}}:
            !param{caption}
!figure{result}{0.8\textwidth}:
    Result of the experiment
~~~

展開後:

~~~tex
\includegraphics[width=0.8\textwidth]{fig/result.pdf}
\begin{center}
\begin{minipage}{0.8\textwidth}
Result of the experiment
\end{minipage}
\end{center}
~~~

補間できるのは、生の TeX 行、コマンド・環境のインライン `{...}` / `[...]` / `<...>`、
`@{...}` のヘッダー、ユーザーマクロへ渡す必須インライングループである。
標準フロー制御（11.1節）もこの意味ではユーザーマクロなので、
`!before{\vspace{!text{gap}}}` はただの呼び出し値として補間できる。
別マクロの引数は、呼び出し側テンプレートの束縛を使って補間してから渡す。
挿入された文字列は再走査も再パースもせず、`!text{x}` や `@frame`、`>>` という
綴りを含んでも構文にはならない。`>>` 合成でも同じ規則が適用される。

raw mode 領域（`!BEGIN_RAW_MODE` から対応する `!END_RAW_MODE` まで）の本文は、この
テキストフィールドの補間対象外である。本文は完全に verbatim に扱われるため、
`!text{...}` はその綴りのまま出力され、領域内では `!!` / `@@` の行頭 escape も
働かない。

値が**ちょうど1個の `RawTex` ノードからなる場合のみ**、文字列として取り出せる。
`!m{hello}`、`!m{}`、1行だけの本文は使える。2行以上の本文、空の本文、環境などの
構造値は使えない。構造値を挿入する場合は `!param` を使う。rest parameter 全体は
補間できないが、`!each` の item が1個の `RawTex` なら補間できる。

~~~text
!defmacro{labels}{...items}:
    !each{items}{item}:
        \label{item:!text{item}}
!labels{alpha}{beta}
~~~

コンパイラが読む情報（フラグ名、マクロ名・パラメータ名、import path、構造名、
`(...)` 束縛リスト）には補間できない。残っている組み込み special の引数も
すべて対象外である。レジストリに残っているのはコンパイラ側のメタデータを
指す名前だけだからである。これらの引数では、エスケープを付けても
marker の綴りを許可しない。

テンプレート外の `!text{...}`、AST 位置の `!text`、テキスト中の `!param{...}` は
マクロエラーになる。不正な名前・閉じていない hole・未知のパラメータもエラーになる。
テンプレート内の診断は定義位置を指し、呼び出し位置と展開経路も示す。
捨てられた `!when` / `!unless` の payload は補間も検査もされない。

文字どおりの marker を書くには、テキストフィールド中で `!!text{x}` / `!!param{x}` と
書くと、それぞれ `!text{x}` / `!param{x}` が出力される。`\!text{x}` はそのまま残る
（`\!` は TeX コマンド）。`!text {x}` / `!textbf{x}` / `!text` は marker ではない。
行頭では先に raw-line escape が働くため、二層になる:

| ソースの行頭 | parser 後 | 補間後 |
| --- | --- | --- |
| `!!text{x}` | `!text{x}` | パラメータ `x` の文字列（テンプレート外ではエラー） |
| `!!!text{x}` | `!!text{x}` | リテラル `!text{x}` |

文字列の由来は断片ごとに保持する。値の断片は元の値の位置、テンプレートのリテラル部は
マクロ呼び出し位置を指す。列情報のない SyncTeX では値を優先する。ただし、1つの出力行に
異なるソース行由来の値が複数ある場合は、従来同様に逆引き先が曖昧としてエラーになる。
詳細な診断と実装設計は [文字列 interpolation 設計書](string-interpolation.md) を参照。

## 13. ビルドフラグ（Build flag）

ビルドフラグは、1つのソースから同じ文書の複数のバージョンを生成するための真偽値である。`!flag` がフラグとその既定値を宣言し、`!when` と `!unless` が、1つのフラグ、あるいは `[and]` / `[or]` モディファイアでまとめた複数のフラグに応じて、ペイロード全体を残すか捨てるかを決める。

この**平坦な畳み込み1段**が条件機能のすべてである。畳み込みの中に括弧や別の畳み込みを書くことはできず、畳み込みの中の個別のフラグだけを否定することもできない。それ以上の組み合わせは `>>` による条件そのものの合成で書く（条件のネスト自体は制限されない）。条件式・比較演算・`on` と `off` 以外の値は v1 には存在しない。

### 13.1 宣言（!flag）

~~~text
!flag{draft}{off}
!flag{handout}{on}
~~~

宣言は必須インライングループをちょうど2つ取る。1つ目がフラグ名、2つ目が既定値であり、既定値は `on` または `off` のいずれかでなければならない。suite は受け付けない。フラグ名には `[A-Za-z][A-Za-z0-9_-]*` の文字パターンが使用できる。

`!flag` は**トップレベル専用の文**である。suite の内部に置くことも、`>>` のセグメントにすることもできない。同じ名前を再宣言した場合は、最初の宣言位置を指し示すバリデーションエラーとなる。宣言自体は TeX コードを出力しない。

すべての宣言は条件が読まれる前に収集されるため、宣言より前の位置で `!when` を書く前方参照が可能である。

### 13.2 コマンドラインからの上書き

宣言された既定値は、コンパイル時に上書きできる。

~~~text
texflux compile talk.tfx -o talk.tex --flag draft --flag handout=off
~~~

`--flag NAME` はフラグを on にする。`--flag NAME=on` と `--flag NAME=off` は明示形である。

**どの宣言にも一致しない名前を指定した場合はエラーになる。**同じフラグを2回指定した場合、および `on`/`off` 以外の値を与えた場合も同様にエラーとなる。つまり、タイプミスが黙って無視されることはない。

### 13.3 !when と !unless

~~~text
!when{draft} >> \marginpar{発表前に測り直す}

!unless{handout}:
    \pause
    @{\small} >> \textit{ここでテールレイテンシについて触れる}
~~~

いずれも、宣言済みのフラグ名を指す必須インライングループを1つ以上取る。ペイロードは `:` ブロックスイート、または `>>` 合成の残り部分のいずれかで書く。シーケンススイート（`::`）、ペイロードの欠落、未宣言のフラグ名、同じフラグの重複指定は、いずれもバリデーションエラーとなる。

`!when` はフラグが on のとき、`!unless` は off のときにペイロードを残す。

残されたペイロードは、それ自身のグループで包まれることなく、外側のブロックへそのまま挿入（splice）される。

### 13.4 [and] と [or]

先頭のオプショングループで、複数のフラグを1つの判定に畳み込める。

~~~text
!when[or]{draft}{internal} >> \marginpar{発表前に測り直す}
!when[and]{notes}{handout}:
    ...
~~~

モディファイアは `[and]` と `[or]` のみである。フラグを2つ以上指定する場合は**必須**であり、モディファイアなしで2つ並べた場合は暗黙の論理積にはならずエラーとなる。フラグ1つに対して付けることは許容される（何も変わらない）。モディファイアとして読まれるのは先頭のグループのみで、それ以外の位置にあるオプショングループはフラグ名として読まれ、そこでエラーになる。

`!unless[X]` は、対応する `!when[X]` **全体の否定**である。したがって「どちらでもない」は `[or]` で、「両方ではない」は `[and]` で書く。

~~~text
!when[and]{a}{b}     a と b が両方 on のとき残す
!when[or]{a}{b}      a か b のどちらかが on のとき残す
!unless[and]{a}{b}   a と b が両方 on のときだけ捨てる（＝両方ではない）
!unless[or]{a}{b}    a か b のどちらかが on なら捨てる（＝どちらでもない）
~~~

畳み込みの中で一部のフラグだけを否定することはできない。`a かつ b でない` のような条件は、従来どおり合成で書く。

~~~text
!when{a} >> !unless{b} >> \note{...}
~~~

### 13.5 解決とその範囲

フラグはマクロ展開の前に解決され、条件はマクロ展開の途中で解決される。したがってフラグ関連の構文が正規化処理やレンダラーに漏れ出ることはない。マクロテンプレート内部に書かれた条件は、そのテンプレートが実体化される時点で解決される。

**捨てられたペイロードは展開も正規化もされない。**そのため、コンパイルが通らなくなった箇所を一時的に無効化したまま文書をビルドできる。未知の special、引数の数が合わないマクロ呼び出し、トップレベル以外の `!defmacro` は、いずれも捨てられる側にあれば報告されない。

捨てられるペイロードが満たしていなければならないのは、**条件の解決より前に行われる検査のすべて**である。すなわち、構文として解釈できること、`!flag` がトップレベルの文であること、`!macroimport` もトップレベルの文であり `>>` のセグメントにならないこと、そして 12 章のテンプレートの規則（`!defmacro` を `>>` のセグメントにしないこと、`!each` が自前の `:` を持つこと、テンプレート内に `!import` / `!macroimport` を書かないこと）の4つであり、これがその全部である。

この4つはいずれも「その行をどこに書いたか」という純粋に構文的な問いであり、**ファイルを1つも開かない**。したがって、コンパイルが通らなくなった内容も、存在しなくなった依存先も、どちらも `!when` で無効化したまま文書をビルドできる。

条件が消すのは**文であって引数ではない**。値が捨てられたシーケンスエントリはエントリとして残り、空の引数として出力される。

~~~text
\cmd::
    - !when{draft} >> \x
    - tail
~~~

`draft` が off のとき、これは `\cmd{}{tail}` を出力する。

## 14. モジュール（Module）

1つのファイルが1つのモジュールである。`.tfx` は**コンテンツモジュール**、`.tfxm` は
**マクロ定義モジュール**であり、これらを合成する構文は2つある。この2つは目的が異なるため、
決して1つの汎用 import にまとめられることはない。

~~~text
!macroimport{layout.tfxm}   マクロ名前空間の依存。TeX 出力を生まない
!import{slide.tfx}          コンテンツの依存。正準 AST を生む
~~~

### 14.1 コンテンツモジュール（.tfx）

`.tfx` には、生の TeX、構造化構文、`!flag`、`!defmacro`、`!macroimport`、`!import`、
条件、および通常の本文を書ける。

`!import` は対象を**独立した1つのモジュールインスタンス**としてコンパイルし、
その結果の正準 AST を import した位置に挿入する。呼び出し先のローカルなフラグ名と
マクロ名は、呼び出し側のテーブルに一切入らない。したがって2つのモジュールが
それぞれ `draft` を宣言していても、それぞれ `!box` を定義していても衝突しない。

パース結果はキャッシュされるが、**コンテンツ import は1回ごとに別インスタンス**である。
同じモジュールを2回 import すれば、その内容は2回出力される。

### 14.2 マクロモジュール（.tfxm）

`.tfxm` に書けるのは `!defmacro`、`!macroimport`、コメント行、空行だけである。
`!flag`、`!when`、`!unless`、`!import` は、**テンプレートの内部を含めてファイル中のどこに
あってもエラー**になる。マクロモジュールはフラグを宣言できないため、その内部の条件は
「そのモジュールを実体化したコンテンツモジュールのフラグ」を暗黙に参照することになり、
マクロ取り込みの語彙性と私的性、そしてキャッシュの健全性が壊れてしまうからである。

マクロモジュールが公開するのは、**自分自身が `!defmacro` したマクロだけ**である。
`!macroimport` で得たマクロは私的な実装依存であり、再輸出されない。
`public` / `private` / `export` に相当する構文は存在しない。

マクロモジュールは**自己完結**していなければならない。テンプレート中で使う `!名前` は、
テンプレート専用構文、組み込み special、標準フロー制御、自分が定義したマクロ、
自分が取り込んだマクロのいずれかでなければならない。呼び出し側の無関係な名前空間が、本来不正なマクロモジュールを
正当化することは決してない。

### 14.3 !macroimport

~~~text
!macroimport{style-v2.tfxm}
~~~

必須のインライングループをちょうど1つ取り、suite も束縛リストも取らない。
`!flag` と同じ理由で**トップレベルの宣言**であり、`>>` のセグメントにはできない
（マクロ名前空間がビルドフラグに依存すると語彙的スコープが成立しなくなる）。
同じモジュールを1つのファイル内で2回取り込むこともエラーである。

マクロ定義は**語彙的スコープ**を持つ。テンプレート中の名前は、それを定義した
モジュールの環境で解決され、呼び出し側の環境では解決されない。

~~~text
% core.tfxm
!defmacro{wrapper}{body}:
    @{\small} >> !param{body}
~~~

~~~text
% A.tfxm
!macroimport{core.tfxm}

!defmacro{foo}{body}:
    !wrapper:
        !param{body}
~~~

~~~text
% main.tfx
!macroimport{A.tfxm}

!foo:
    Hello
~~~

これは動作する。しかし `main.tfx` から `!wrapper` は**見えない**。
`!macroimport` は私的かつ非推移的だからである。この性質により、
ダイヤモンド型の取り込みは自動的に隔離される。

スコープが語彙的であることから、マクロの同一性は名前だけでなく、
定義元モジュールと名前の組である。再帰検出もこの同一性に従う。
したがって、あるテンプレートが別のモジュールのたまたま同名のマクロを呼んでも、
それは循環ではない。展開チェーンは、1つのモジュール内に収まる間は名前のみで、
モジュールをまたいだ時点で `name@file` の形で綴られる。
またいだ先では名前だけではマクロを特定できないからである。

名前の衝突はシャドーイングされず、すべてエラーである。取り込み同士、
取り込みとローカル定義、予約語・組み込み special 名・標準フロー制御の名前との
衝突のいずれも同じで、「後の import が勝つ」という規則は存在しない。

`.tfxm` が純粋である限り、マクロモジュールの循環取り込みは許される。
コンパイラはそのようなグラフを無限にたどってはならない。

### 14.4 マクロライブラリのバージョン併存

これが本機能の中心的な利点である。

~~~text
old-slide.tfx:  !macroimport{style-v1.tfxm}
new-slide.tfx:  !macroimport{style-v3.tfxm}

main.tfx:
    !import{old-slide.tfx}
    !import{new-slide.tfx}
~~~

各コンテンツモジュールは、自分の正準 AST が結合される前に自分のマクロを展開し終えている。
そのため古い本文は古いマクロ定義のまま、新しい本文は新しい定義のまま、
1つの文書に安全に共存できる。`A.tfxm` が `core-v1.tfxm` を、`B.tfxm` が `core-v2.tfxm` を
取り込んでいる場合も同様である。

### 14.5 !import

~~~text
!import{slide.tfx}
!import{quiz.tfx}(answers=on)
!import{quiz.tfx}(answers=$answers, memo=off)
~~~

パスを表す必須インライングループをちょうど1つと、末尾の束縛リスト `(...)` を
最大1つ取る。`!import` は**内容を生む構文**なので、suite を取らず、`>>` のラッパーにも
なれない。コンテナや TeX グループで囲みたいときは次のように書く。

~~~text
@center >> !import{slide.tfx}
@{} >> !import{legacy-slide.tfx}
~~~

`!import` は**文が書ける場所ならどこでも**有効である。トップレベル、ブロック suite の中、
シーケンス値の中、そして条件のペイロードの中でも書ける。

~~~text
!when{appendix}:
    !import{appendix.tfx}
~~~

条件で捨てられたペイロード内の `!import` は**コンパイルされず、そのファイルは開かれない**。
したがってコンテンツの依存グラフはビルド構成に依存しうる。

マクロテンプレートの中に `!import` を書くことはエラーである。そうしないと
コンテンツの依存関係の発見がマクロ展開に依存してしまう。ただし `!import` を
マクロの**値として渡す**のは有効であり、テンプレートがその値を2回参照すれば
モジュールインスタンスは2つ生成される。

同じモジュールの繰り返し import は許されるが、循環はエラーである。判定は
**アクティブな import スタック**に対して行われ、「一度でも見たパスか」では判定しない。

~~~text
main.tfx:  !import{slide.tfx}
           !import{slide.tfx}       % 合法。2つのインスタンス

A.tfx -> B.tfx -> A.tfx             % エラー
~~~

### 14.6 import のフラグ束縛

束縛リストは、取り込む側が呼び出し先の宣言済みフラグを設定する構文である。

~~~text
% quiz.tfx
!flag{answers}{off}

@frame{問題}:
    問題文
    !when{answers}:
        答え: 42
~~~

~~~text
!import{quiz.tfx}                      % 呼び出し先の既定値 (off)
!import{quiz.tfx}(answers=on)          % リテラルで上書き
!import{quiz.tfx}(answers=$answers)    % 呼び出し側のフラグを転送
!import{quiz.tfx}(answers=$answers, memo=off)
~~~

値に書けるのは `on`、`off`、`$呼び出し側フラグ名` の3つだけであり、式言語は導入されない。
束縛されなかった呼び出し先のフラグは、**呼び出し先自身の既定値**のままである。
**同名フラグの暗黙の継承は存在しない**ので、モジュールをまたぐ設定は常に明示的である。
コマンドラインの `--flag` はビルドを設定するものなので、**ルートモジュールにのみ**適用される。

次はいずれもエラーである。

- 空の束縛リスト `()`
- 束縛の書式が不正なもの
- 呼び出し先が宣言していないフラグ名
- 呼び出し側が宣言していない `$名前`
- 同じ呼び出し先フラグを2回束縛すること

### 14.7 パスの解決

コンテンツ import もマクロ import も、**それを書いたファイルからの相対パス**で解決される。
親がどこから取り込んだかには依存しない。これが再利用可能なコンポーネントの可搬性を支えている。

~~~text
archive/2024/slide.tfx
archive/2024/macros.tfxm
~~~

`slide.tfx` 内の `!macroimport{macros.tfxm}` は、どこから取り込まれても
`archive/2024/macros.tfxm` に解決されなければならない。

パスの区切りは `/` のみで、相対パスでなければならず、構文に応じた拡張子
（`!import` は `.tfx`、`!macroimport` は `.tfxm`）を持たなければならない。
`..` は使える。依存の追跡に使われる識別子は正規化されたファイルシステムパスである。

### 14.8 生の TeX とモジュール境界

TeXFlux はコンテンツモジュール内の生の TeX を検証しない。`\newcommand` などの
生 TeX マクロは TeXFlux の名前空間システムの外にあり、自動的に隔離されることはない。
`!import` は既定で**透過的な**内容の取り込みである。TeX レベルのグループ化が必要なら、
既存の構造化構文で明示する。

~~~text
@{} >> !import{legacy-slide.tfx}
~~~

### 14.9 コンパイル順序と診断

~~~text
マクロ・フラグ・macroimport の形式検査
 -> 純粋な >> 脱糖
 -> ビルドフラグの収集 -> import 束縛 または --flag 上書き
 -> マクロ import の解決と語彙的環境の構築
 -> ソースマクロの収集
 -> 条件の解決とマクロ展開
 -> コンテンツ import の再帰的解決
 -> 値の消費と special 展開
 -> 正準 AST の検証
 -> レンダラー
~~~

モジュールの解決はフロントエンドの責務である。モジュール構文が正規化処理や
レンダラーに到達することはない。

取り込まれた正準 AST は**呼び出し先のスパンを保持する**。生成された TeX は、
その行を実際に書いたファイルへ対応づく。取り込まれた内容が呼び出し側の `!import` 行に
付け替えられることはない。`.tfxmap` はこれに応じて複数のソースを持つ。

被 import モジュール内で起きたエラーは、**自分のスパンをそのまま保持**し、
メッセージの末尾に import 元の位置を付け足す。入れ子の import では内側から順に積み上がる。

~~~text
c.tfx:4:16: validation error: duplicate macro parameter 'x';
imported from b.tfx:3:1; imported from main.tfx:7:1
~~~

マクロモジュール内で起きたエラーにも、同じように `!macroimport` の位置が積み上がる。
`.tfxm` は複数の文書から共有されるので、どの取り込みがそれを引き込んだかが
問題の在処を示すからである。各モジュールが記録する取り込み位置は 1 つだけなので、
その記録は木を成し、根まで辿る処理は必ず停止する。エラー自身の行を指す段は
情報を足さないので読み飛ばすが、そこで**打ち切りはしない**——そのファイル自体が
どう取り込まれたかは依然として答えの一部である。1 つのモジュールが複数箇所から
取り込まれている場合、記録されるのは最も浅い段であり、
読み順で最初とは限らない。

~~~text
impure.tfxm:2:5: module error: '!nosuchmacro' is not defined in impure.tfxm
and is not available through its own !macroimport;
imported from mid.tfx:1:13; imported from main.tfx:1:1
~~~

### 14.10 同梱される標準マクロモジュール

11.1節の標準フロー制御は、コンパイラに同梱され TeXFlux 本体と同じバージョンで
配布される1つのマクロモジュールに置かれている。これは 14.2 節の規則をすべて
満たす普通の純粋な `.tfxm` である。中身は `!defmacro` とコメントと空行だけで、
フラグも条件分岐も本文も、自分自身の import も持たない。

セッションが作るマクロ環境は、すべてこのモジュールから seed される。ルート
モジュール、`!import` で辿った `.tfx`、`!macroimport` で辿った `.tfxm` の
いずれもが対象なので、マクロモジュールのテンプレートからもこの5つを呼べる。
概念としては、各モジュールの明示的な import の前に暗黙の import が1行あるのと
同じだが、実装は環境に seed するだけであり、利用者の AST に合成された
`!macroimport` ノードを差し込むことはしない。`prelude` という構文も `std.*`
という名前空間もなく、別の prelude を選ぶ手段もない。

seed は優先順位の層ではない。標準名がすでに見えているスコープでは、その名前を
定義することも import することもできないので、「ローカル＞明示 import＞標準」
のような順序も、import 順に依存する挙動も生じない（12.1節・14.3節）。

このモジュールはコンパイラの配布物の中から解決され、利用者のプロジェクト
ディレクトリを基準にすることはない。1回のコンパイルにつき読み込みは高々1回で
ある。lexical scope 上の識別子は合成された名前であり、インストール先のファイル
パスは言語意味論の一部ではない。ソーススパンにも現れず、文書のソースとしても
数えないので、`.tfxmap` にも外部 AST の `sources` にも出てこない。テンプレート
由来の scaffolding は通常のマクロと同じく呼び出し位置へ付け替えられ（12.6節）、
展開後の正準 AST には標準フロー呼び出し専用のノード型は一切残らない。

同梱モジュール自体がパースや検証に失敗した場合、それは文書の誤りではなく
インストールまたはコンパイラの不具合であり、そのように報告される。

## 15. 引数の中括弧の位置

シーケンス値の形そのものが、生成される中括弧の位置を決める。1行に収まる値は
中括弧が密着し、複数行にわたる値は中括弧が独立行になる。指定のためのマーカーは
存在せず、短い引数は短いまま、構造を含む引数は読みやすいままになる。

~~~text
\command::
    - short
    - @center:
        figure
~~~

~~~tex
\command{short}{
\begin{center}
figure
\end{center}
}
~~~

別のレイアウトが欲しい場合は、著者が中括弧を自分で書く。値が生の TeX であり
`{` で始まって対応する `}` で終わるなら、その中括弧が引数自身の中括弧とみなされ、
テキストは逐語的にコピーされる。つまり書いた位置にそのまま出力される。

~~~text
\command::
    - {fooo
      bar
      }
    - {
      a
      c}
~~~

~~~tex
\command{fooo
bar
}{
a
c}
~~~

このスキャンは対応する中括弧を見つけるだけであり、中身を解釈することはない。
一つの均衡した（balanced）グループとしてスキャンできない値は生成された中括弧の
ままになるため、誤りは「余分な中括弧が見える」形で現れ、引数の個数が黙って
変わることはない。値自体を TeX グループにしたい場合は、複数行で書けば生成形に
なる。

密着した閉じ中括弧は、TeX のコメントの後ろでは飲み込まれてしまう。値の最終行が
**丸ごとコメント**である場合、閉じ中括弧は独立行のまま保たれ、警告が出力される。
最終行にエスケープされていない `%` が**含まれるだけ**の場合は、警告のみを出して
密着のままにする（動かすには著者の TeX を書き換えることになるため）。`\%` は
コメントではない。警告は値の位置情報を示し、コンパイルを失敗させることはない。

## 16. 空行、生の TeX、コメント

シーケンスモードにおいて、各エントリー（`-`）の間に置かれた空行は単なる区切り文字（separator）として扱われ、値の一部には含まれない。一方、各シーケンスエントリーのブロック内部や、ブロックモード（`:`）の内部にある空行は、意味のある内容（content）としてそのまま保持される。

TeX グループ内部に書かれた `:`、`::`、`>>`、パイプ `|` は、すべて生のテキストとして扱われる。構造化構文の先頭位置でエスケープに用いる `@@` / `!!` を除き、生の TeX コード行が TeXFlux の構文として再解釈されることはない。

構造化ヘッダーの末尾に TeX 形式のコメント（`% ...`）を付加することは、未定義ではなく明確に禁止されている（パースエラーとなる）。通常の生の TeX 行に含まれるパーセント記号（`%`）は、そのまま出力される。

## 17. 構文 AST と正準 AST（Syntax AST / Canonical AST）

パーサーは、元の構文の形状（syntax shape）とソースコード上の位置情報（source span）を保持する。代表的な構文ノード（syntax node）は以下の通りである。

- `RawTex`
- `ParsedInvocation`（command、named environment、brace、transparent）
- `SpecialInvocation`
- `Stack`
- `SequenceEntry`
- `Block`

suite のモード情報としては `Sequence` または `Block` を保持する。suffix を持たないスタックには suite は存在しない。`SequenceEntry` は、`-` マーカー自体のスパンと、値全体のスパンを保持する。

正規化パイプライン（normalization pipeline）の流れは以下の通りである。モジュールに関する段の詳細は 14.9 節が定める。

~~~text
物理行（physical lines）
  -> 構文 AST（syntax AST）
  -> 純粋な >> の脱糖（pure >> desugaring）
  -> ビルドフラグの収集（build flag collection）
  -> マクロ import の解決（macro import resolution）
  -> ソースマクロの収集・条件の解決・展開（macro and conditional expansion）
  -> コンテンツ import の解決（content import resolution）
  -> 値の消費 / special の展開（value consumption / special expansion）
  -> 正準 AST（canonical AST）
  -> レンダラー（renderer）
~~~

正準 AST（canonical AST）を構成するノードは以下のものだけに限定される。

- `RawTex`
- `GenericInvocation`
- `Argument`
- `Block`
- `BraceGroup`

正規化処理を経た後に、`ParsedInvocation`、`SpecialInvocation`、`Stack`、`SequenceEntry` などの構文固有ノードがレンダラーに届くことは決してない。

`GenericInvocation` は、`body=None` の場合はコマンドを表し、`body=Block` の場合は名前付き環境を表す。`BraceGroup` は必ずリテラルな TeX 中括弧（`{ ... }`）を出力する。透過コンテナ（Transparent container）はラッパーノードを生成しない。

## 18. 位置情報（SourceSpan）、ソースマップ、SyncTeX

主要な構文ノード、正準ノード、およびエラー診断情報（diagnostic）は、ファイル名、1から始まる行番号（1-based line）、1から始まる列番号（1-based column）の情報を保持する。スパンは半開区間（half-open）で表される。少なくとも以下の要素について、元のソースコードの位置（provenance）が保持される。

- suite のコロン（`:` / `::`）
- シーケンスの各 `-`
- シーケンス値のブロック境界
- `@{...}` ヘッダー
- `@:` / `@::` ヘッダー
- スタックの各セグメント（`>>`）
- 閉じたスタックの終端要素
- シーケンスおよびブロック値の境界
- リスト項目（item）のメタデータ
- 生成された `\begin` / `\end`、引数の中括弧、リテラル中括弧、special 展開部分

レンダラーは `MappedEmitter` を介して、生成された TeX の出力範囲と元のソースコードの位置情報を対応づける。ソースマップ（source map）は、生成された TeX と元の `.tfx` ソースファイルのハッシュ値を検証する。ソースマップは、コンパイルが読み込んだソースファイルを列挙する。ルートは必ず含まれ、import されたモジュールは1つ以上の対応を生んだ場合に含まれる。ルートは id 0 であり、import を持たない文書のソースマップはモジュール機構の導入前と完全に同一である。SyncTeX のリマップ処理は、このソースマップを利用して生成された TeX の `Input` タグを元のソースファイルへとマッピングし直す。

言語仕様や構文の拡張にあたっても、このソースマップおよび SyncTeX の連携機構を削除したり簡略化したりしてはならない。

## 19. エラー診断（Diagnostics）

`ModuleError`（`module error`）は、モジュールシステムに関する診断を表す。
import の形式、パスの解決、コンテンツ import の循環、`.tfxm` の純粋性と自己完結性、
モジュール間のマクロ名の衝突、そして import のフラグ束縛がこれに含まれる。

raw mode のマーカーに関する代表的な診断は次のとおりである。

- 対応する END のない BEGIN: `'!BEGIN_RAW_MODE' is not closed by '!END_RAW_MODE'`
- 領域外の END: `'!END_RAW_MODE' has no matching '!BEGIN_RAW_MODE'`
- マーカーが単独行でない場合（payload、`>>`、群、suffix、コメント付き）:
  `'!BEGIN_RAW_MODE' must stand alone on its own line`（END も同様）

いずれも `ParseError` であり、通常の `file:line:column: parse error: ...` 形式で
マーカーまたはセグメントの位置を示す。

以下の記法は、現行の v1 ではサポートされない。

- suffix を持たない単独の名前付き環境 / コンテナ
- シーケンス suite（`::`）において、マーカー（`-`）の付いていない子要素
- 閉じたスタック構文において、終端がオープンなコンテナで終わっているもの
- 未知の special（`!`）
- 構造化ヘッダー行末尾の不要なトークンやコメント
- suite の末尾に `|-` などの他のブロックスカラー変種を付加する記法

削除された `!block`、`!arg`、`!body`、`!items`、`!vpad` は互換用エイリアスとしては提供されず、未知の special としてエラーになる。

## 20. 概念文法（Conceptual grammar）

以下の文法定義は、TeX 本文の文法ではなく、TeXFlux の構造化構文の意味関係を表すための概念文法（conceptual grammar）である。

~~~text
document          ::= statement*

statement         ::= structural-expression | raw-mode-region
raw-mode-region   ::= "!BEGIN_RAW_MODE" NEWLINE verbatim-line* "!END_RAW_MODE"

suite-suffix      ::= sequence-suffix | block-suffix
sequence-suffix   ::= "::" SP*
block-suffix      ::= ":" SP*

sequence-suite    ::= sequence-entry*
sequence-entry   ::= "-" SP* sequence-block
sequence-block    ::= first-line continuation-line*
first-line        ::= inline-value | structural-expression
continuation-line ::= indented TeXFlux line

structural-expression
                  ::= segment (stack-separator segment)* suite-suffix?
stack-separator   ::= SP+ ">>" (SP+ | SP* NEWLINE SAME-INDENT)

segment           ::= command-segment
                    | named-container-segment
                    | brace-container-segment
                    | transparent-container-segment
                    | special-segment

command-segment  ::= "\\" command-name group*
named-container-segment
                  ::= "@" environment-name group*
brace-container-segment
                  ::= "@{" balanced-raw-tex "}"
transparent-container-segment
                  ::= "@"
special-segment  ::= "!" special-name group* binding-list?

flag-declaration  ::= "!flag" "{" flag-name "}" "{" ("on" | "off") "}"
combinator        ::= "[" ("and" | "or") "]"
conditional       ::= ("!when" | "!unless") combinator? "{" flag-name "}"+
                      (block-suffix | SP+ ">>" SP+ segment ...)

macro-import      ::= "!macroimport" "{" module-path "}"
content-import    ::= "!import" "{" module-path "}" binding-list?
binding-list      ::= "(" SP* binding (SP* "," SP* binding)* SP* ")"
binding           ::= flag-name SP* "=" SP* ("on" | "off" | "$" flag-name)
~~~

実際の実装におけるパーサーは、リスト項目のメタデータ、括弧の対応関係、ソースコード上の位置情報（source span）、および生の TeX 行のインデントなどを別途管理している。`sequence-block` は、同じインデント階層に次の `-` が現れるまで継続する。この文法の要点は、**二重コロン（`::`）が「`-` ごとに1つのブロック値」を意味し、単独のコロン（`:`）が「全体で1つのブロック値」を意味し、suffix なしが「すでに完結した値」を意味する**という点にある。
